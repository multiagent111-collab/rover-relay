# Optional vehicle advice 1.0

This generic, stateless service reviews a sanitized current provider snapshot. It has no private ROVER dependency, database, H-MEM writer, Zetaris requirement, dispatch, offer, reservation or booking authority. The caller must authenticate its user, derive tenant membership, enforce provider mappings and revalidate at confirmation in its own backend.

Start Nightshift with a working compute provider. Configure `METERLESS_BASE_URL`, `METERLESS_RUNTIME_TOKEN`, `METERLESS_ROUTE=meterless/auto` and a separate server-only `RELAY2_ADVICE_TOKEN` of at least 32 characters. Run `node --import tsx src/vehicle-advice-server.ts`. It binds loopback port 4196 (`RELAY2_ADVICE_PORT` overrides). For Windows system trust, start the Node process with `NODE_USE_SYSTEM_CA=1`. Keep credentials in private runtime configuration, never source or a browser/mobile app.

`GET /v1/health` reports service health, **not verified inference**. `POST /v1/integration/vehicle-advice` requires its own Bearer server credential. The strict `vehicle-advice-input-1.0` contract accepts a run UUID, saved request revision, selected mapped provider UUID, service/vehicle type, completeness/schedule/requirements flags, confirmed-memory flags/revision, and at most 20 current eligible mapped provider UUIDs. Snapshot validity cannot exceed 30 seconds. No addresses, coordinates, service notes, raw requirements, user/tenant IDs or credentials are accepted.

Planner and Critic are separate calls through the existing Nightshift transport, with the same input and shared abort signal. They are roles, not evidence of separate models or independent providers. The runtime chooses the actual route; the response-reported model and bounded correlated receipt projection are recorded. Runtime receipt metadata is not a verified cryptographic attestation. No prompt previews, hidden reasoning, prose explanations or credentials are returned or logged.

The Planner retains the selected provider if eligible, otherwise proposes the first supplied eligible provider **as advice only**. Reasons are bounded factual codes. Missing pickup/destination, any unverified requirements, or future scheduling requires clarification. Current snapshots cannot prove future availability or special requirements. A separate Critic reviews the same request revision, snapshot and proposal. Deterministic validation runs in addition to model critique, with visibly different activity kinds.

Outputs use `vehicle-advice-1.0`: `valid_proposal`, `clarification`, `infeasible`, `stale_evidence`, `rejected`, or `inference_unavailable`. A stale snapshot or Critic refresh request returns no proposal. Malformed schemas and failed critiques allow **one targeted Planner repair**, followed by another Critic only if the repaired proposal passes validation. Four inference attempts and a single 180-second deadline bound the entire run, including repairs. Transport/authentication failures are not automatically retried; an explicit new review is read-only. No confirmation or new-intent retry exists here. At most two runs execute concurrently. Inference outages do not substitute sample output.

The caller must keep ordinary requesting separate from advice, reject mismatched revisions and snapshot IDs, display expiry and preserve explicit user choice. It must never treat an advice provider as approval to switch providers or to submit a request. A lost gateway response cannot establish whether upstream inference ran; zero locally observed call records are not proof of zero upstream work.

Run `npm test` and `npm run build`. Controlled tests cover clarification, no providers, invented providers, mismatched context, schema repair, critique rejection, expiry, timeout, authentication and no automatic fallback. These are not live sponsor evidence. A real device/gateway review and receipt correlation are required for a live-integration claim.

A completed model review can outlast the original snapshot. The service returns `reviewedProposal` separately from the actionable `proposal`. A stale review has no actionable proposal. The authenticated caller may revalidate it once, using fresh source facts for the same request revision and exactly the same eligible mapped provider IDs and vehicle types. If facts changed or the read fails, advice stays stale. ROVER records this deterministic revalidation separately, with a new snapshot ID and timestamps in `freshness`; it never claims the models saw the later snapshot. The model snapshot ID and original timestamps remain unchanged. Confirmation still performs its own independent fresh check.

The four-call ceiling counts logical Nightshift completion requests. The runtime may race multiple configured provider routes internally; its reported race width is retained in routing metadata. This application does not silently select a fallback inference provider or change Nightshift policy.
