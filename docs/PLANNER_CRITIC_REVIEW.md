# Checked proposals and bounded repair (RELAY-04)

Relay's internal model contract is now `proposal-2.0`. Both Planner and Critic are invoked separately. The Planner selects an ID and citations and copies structured terms: exact confirmed SKU, quantity, destination, budget in integer cents, original minute limit, confirmed entrance, checked total cents and travel/handling minutes. It must declare `commitment: "uncommitted"` and a controlled explanation code. Free-form summaries and extra booking/reservation/tool fields fail the strict contract. Source and memory text remain untrusted data.

The deterministic validator compares every term with the confirmed request, effective recalled entrance and enumerated candidate. It checks candidate identity and all required feasibility checks independently of the Critic. Selected candidates must cite precisely their supplier, courier and route observations, with no omissions, duplicates or unrelated IDs. Null reports require the union of checked candidate observations and null estimates; null is rejected when a checked option exists. No checked option is a report about available evidence, not a guarantee that delivery is impossible everywhere.

Critic responses contain only `approved`, at most ten `{code, field}` issues and `refreshEvidence`. Approval with issues or a refresh request is contradictory and fails. Invalid Critic schemas fail closed. Codes include `candidate_infeasible`, `evidence_missing`, `evidence_invalid`, `request_mismatch`, `terms_mismatch`, `unsupported_claim` and `feasible_option_exists`. Server-authored repair instructions include exact missing citation IDs or expected field values. The model cannot supply executable actions or arbitrary repair prose.

There is one initial attempt and **one targeted repair**, within the existing ceiling of three rounds, six total inference slots, six logical reads and one 180-second overall deadline. The stricter two-attempt limit ordinarily needs at most four Planner/Critic calls; a malformed Planner skips the Critic on that attempt. Extraction/selection and refreshes still share the RELAY-03 budgets. At most one refresh occurs, only while a repair remains. Repair exhaustion returns `reasoning_exhausted`, records safe structured decisions and leaves no approvable plan or task. Cancellation and exhausted shared budgets also block late acceptance.

Receipt version 1.0 remains readable. New receipts add `review` containing the validated internal contract version, terms, commitment and repairs used. Receipt summaries are server templates computed from deterministic cents/minutes and the confirmed request; they contain no model prose. The UI shows those checked sentences and candidate fields. Planner step displays use a controlled label, including for stored legacy receipts, so legacy model summaries are not re-rendered as Planner decisions. This removes the dollar/cents ambiguity structurally, rather than trying to classify arbitrary natural-language financial claims. Models currently explain choices through controlled codes instead of free prose.

Model HTTP transport retains JSON object mode, a 1 MiB response cap, a 30,000-character content cap, explicit output-limit rejection and response-reported model/request identity. Metadata is bounded and validated; a Nightshift route name alone does not attest the underlying provider/model. There is no fallback or new tool authority. The inherited JSON mode, 4096-token setting, truncation guard and provider-specific timeouts are preserved and packaged with their original attribution in this slice. They were present before the RELAY-04 start.

Approval still requires the owner, current version/digest, expiry, original operational deadline, current observations and memory revision. A correct independently approved null report remains `infeasible`; it cannot dispatch. Only explicit approval of a current feasible receipt can reach the existing simulator boundary.
