# Source evidence and reproducible federation

Relay reads the supplier/courier join from Zetaris. The supplier is an independently persisted SQLite HTTP service; courier and route facts come from the standalone PostgreSQL simulator. Relay does not perform a replacement cross-source join. Reconstructing typed domain objects from the federated rows is not independent proof that a remote service performed the join. The real isolated mutation and reader-denial results are recorded in `examples/recorded/relay-02-federation-2026-10-22.json`.

## Candidate coverage

New observations contain `kind` (`supplier`, `courier`, `route_edge`), source alias, record/version, normalized `facts`, SHA-256 `contentHash`, `observedAt`, `fetchedAt`, mode and, for Zetaris, the client query correlation ID. `provenance=application_projection` means these are Relay's normalized projections of query results. Query IDs identify the requests sent to Zetaris; they are not invented server receipts or platform-certified row-level lineage.

A candidate requires its supplier and courier facts and each edge on its pickup/delivery path. Unrelated supplier/courier/edge observations are not required citations. A blocked path uses the entire observed graph to support the absence of an open path. Missing or mismatched facts/hashes/versions fail the evidence check; omitting any required citation fails proposal validation even if a controlled Critic approves. Unknown or duplicate citations also fail validation. The snapshot retains the complete deduplicated evidence set for inspection.

Hashes use recursively sorted object keys and normalized typed facts. IDs identify a fact revision and remain stable across another fetch/query with unchanged content. Query IDs and observed/fetched times remain separate, preserving each query's timing without changing the fact hash. They do not prove real-world truth, supplier holds or independent source identity. Changed stock/version, courier availability, edge cost/closure or source alias changes the hash. Query timing is never used to freshen a cached source timestamp.

Stored receipt schema `1.0` remains readable. New evidence fields are additive and described by `SourceEvidence` in OpenAPI; newly planned candidates require enriched observations. Legacy aggregate route evidence alone cannot satisfy new candidate coverage. Approval still refreshes source data, checks expiry/current terms and requires a replacement proposal when facts change. Evidence is independent of dispatch authority.

## Source response contract

Both candidate and edge SELECT projections include `tenant_id`; the adapter rejects unexpected tenant rows even if a faulty upstream ignores its fixed tenant predicate. The current bearer token maps to one disclosed local tenant (`relay-demo`), not production multi-tenancy. Never accept arbitrary caller predicates or client identity headers as authority.

Only bounded qualified view identifiers are configurable. Snapshot reads use fixed SELECT templates; the public connectivity helper accepts only its fixed `SELECT 1` check. No model-authored SQL executes. Candidate/edge numeric values accept validated numeric strings (including exponent notation) and finite nonnegative integers, not nulls, booleans or empty strings. Booleans and ISO timestamps are validated separately. Invalid fields return a bounded setup error without upstream row contents.

The adapter rejects empty candidate sets, empty or incomplete campus graphs, conflicting duplicate identities/versions/observations, unknown campus nodes, out-of-tenant rows, stale/skewed timestamps, explicit partial-response indicators and queries reaching the 100-row limit. Identical repeated rows deduplicate. The supported campus graph must include all nine base edge IDs, retaining closed edges with `closed=true`; silently dropping edges cannot establish a complete route graph. Additional edges between supported nodes are allowed within the row bound. Each simulator courier supports one supplier corridor; conflicting mappings are rejected rather than silently overwritten.

Supplier `observed_at` comes from its fresh SQLite read. PostgreSQL source views timestamp the statement that reads persisted simulator fixtures; this is a disclosed simulator observation, not a provider heartbeat or last-change timestamp. Zetaris views preserve those timestamps. Observations older than 60 seconds or more than five seconds ahead are rejected. Cache expiry alone cannot establish freshness.

## Provision an independent local clone

Use [local service operations](LOCAL_SERVICES.md) to inspect/reuse existing services. Do not launch the optional Compose profile alongside an already working stack. A new private `.env` uses actual local addresses, keys and fully qualified view names; no filled configuration or password belongs in source control.

1. Initialize Relay's own PostgreSQL simulator database with the application. Inspect its existing `public.relay_couriers_source` and `public.relay_route_edges_source` definitions and role grants before applying any DDL. No DDL was required on the working workstation for RELAY-02.
2. For a fresh database only, apply [source projections](../db/source-views.sql), then use [reader-role template](../db/source-reader.example.sql) with a private psql password variable. The JSON/UTC projection fixes and the registration/view templates were inherited from the October 21 integration and reviewed/packaged in RELAY-02. Their inclusion is not a claim of new federation implementation.
3. The reader needs CONNECT on the dedicated database, USAGE on its schema, and SELECT on only those two views. It must lack raw `relay_state` SELECT and all DML, source-view DML, schema CREATE and elevated role memberships. Inspect effective PUBLIC grants as well. Do not alter shared database policies blindly. The database owner controls projection visibility; the reader never receives the application credentials.
4. Start the independent supplier service. The existing workstation uses 4174; the sample test uses separate supplier storage/port 4184. Zetaris containers normally reach the host service via `host.docker.internal`, and PostgreSQL through the existing shared Docker network. Verify actual addresses in your own setup.
5. Inspect existing Zetaris datasource/table/container/view names first. In your own setup, execute complete [registration template](../db/zetaris-sources.example.sql) statements with a private reader password, then [federated view definitions](../db/zetaris-views.sql). The join must include supplier ID and tenant ID. Do not register raw application state. Existing working definitions are reused; startup does not overwrite them.
6. Set `ZETARIS_CANDIDATE_VIEW=rover_relay.relay_candidates` and `ZETARIS_ROUTE_VIEW=rover_relay.relay_route_edges` for these templates, then run `npm.cmd run preflight:live -- --component=zetaris --json`. This intentionally calls Zetaris and no inference provider. Source observation scope does not attest Nightshift or model identity.

## Verify with controlled and real checks

`npm.cmd test` includes deterministic coverage and adapter injections, explicitly labeled as controlled tests. These tests exercise malformed/stale/partial rows, duplicate conflict detection, scoped coverage, omitted supplier/courier/edge citations, positional projections, unknown SQL and cross-tenant rejection. They do not prove a live sponsor response. `npm.cmd run build` checks the consuming domain/API/UI types.

For a real source proof, use uniquely named synthetic supplier/courier IDs in your own local fixture stores; keep the synthetic courier unavailable so it cannot be selected for dispatch. Confirm the source HTTP response and SQL view reference the intended stores. Add only those isolated records, query the existing join through Zetaris, then change only that supplier's stock and increment its version. A new Zetaris query must return the changed stock/hash while preserving the supplier's real observed time. Remove the owned records in guarded cleanup and query again to confirm absence. Never overwrite original inventory or reset databases; serialize simulator JSON updates with its existing row lock. Keep a private cleanup journal if a test is interrupted.

As the dedicated reader, verify effective SELECT rights on the two views, no raw state SELECT/DML, no view DML, no schema CREATE and no elevated role flags. Zero-row raw SELECT/UPDATE probes must reject with permission denial; a view UPDATE can reject as non-updatable before PostgreSQL checks privileges, so inspect effective grants separately. No actual write should succeed. Reproduce only against your own local simulator, using private credentials. These checks create no mission, reservation, task or real dispatch.

For browser testing, use the isolated offline sample on port 4183, create a plan and inspect Evidence: candidates carry a small required ID set; the full observation list includes route-edge facts/hashes. Existing live processes on 4173/4174 are preserved until an intentional later restart. Build/private ROVER changes remain deferred.
